# Kế hoạch triển khai: Fix B1 crawl lặp, chống spam alert, kiểm toán B3 subprocess

Lưu ý về phạm vi: mình là Claude. Trong phiên này mình chưa đọc được `.codemap/codemap.json` và mã nguồn B1/B3. Vì vậy mọi tọa độ file/symbol bên dưới là giả thuyết. Task 0 bắt buộc xác nhận chúng trước khi sửa. Mình không bịa tên symbol để tránh contract drift.

## 1. Intent & Problem Framing

Vấn đề gốc: B1 không có trạng thái "hôm nay market X đã xong". Mỗi lần cron chạy, nó cào lại từ đầu, ra cùng ~10 ứng viên, tất cả bị dedupe loại, rồi bắn `[B1 VIABILITY ALERT]` vì "không có ứng viên khả thi". Hai lỗi thực ra là một chuỗi nhân quả: thiếu gate đầu vào dẫn đến alert lặp.

Các trade-off chính:

- Nguồn sự thật: `topic_history_registry` là authoritative, lock file chỉ là cache nhanh. Quy tắc SKIP dùng OR: registry HOẶC lock báo đã sản xuất thì skip. Thà bỏ sót một lần chạy còn hơn cào vô nghĩa.
- Thời điểm khóa: chỉ khóa khi COMPLETED thì trong lúc đang sản xuất cron vẫn cào lại. Giải pháp là lock 2 trạng thái: `IN_PROGRESS` (có TTL, ví dụ 6h, chống kẹt vĩnh viễn nếu pipeline chết) và `COMPLETED` (hết hạn tự nhiên khi sang ngày VN mới).
- Múi giờ: bắt buộc `zoneinfo.ZoneInfo("Asia/Ho_Chi_Minh")`. VPS thường chạy UTC, nên dùng `date.today()` sẽ lệch 7h và gây lỗi đúng khung 00:00–07:00 VN.
- Đồng thời: cron chồng lần chạy có thể race. Ghi lock bằng `O_CREAT|O_EXCL` hoặc `fcntl.flock`, ghi JSON qua file tạm rồi `os.replace` (atomic).
- Cooldown alert: chỉ ghi timestamp sau khi gửi thành công. Gửi lỗi thì không ghi, để lần sau còn thử lại. Đếm số alert bị chặn và đính kèm `(+N suppressed)` vào lần gửi kế tiếp để không mất tín hiệu.
- Escape hatch: flag `--force` / env `B1_FORCE_CRAWL=1` để bỏ qua lock khi debug.

## 2. Execution Venue Analysis

- Phát triển và test: `OFFLINE_LOCAL`. Đồng ý với khuyến nghị.
- Runtime: B1 là job cron trên VPS, nên code sau khi sửa sẽ chạy ở `VPS_247`. Cả ba thay đổi (date lock, cooldown, subprocess hardening) đều là logic thuần, không cần gọi LLM. Daily lock còn giảm số lần B1 gọi model, tức là giảm chi phí.
- Về mandate `claude-v4.1-flash` / fallback `claude-6-luna` qua HHTech API: mình không xác minh được hai model ID này tồn tại. Nếu B1 hiện có gọi LLM, Task 0 cần kiểm tra model ID thực tế trong config VPS thay vì giả định. Task này không thay đổi model routing.
- Deploy lên VPS (sync code, restart cron/systemd) là thao tác ảnh hưởng hệ thống đang chạy. Worker phải dừng lại và xin xác nhận trước bước đó.

### 3.1 Schema lock file

Đường dẫn: `<STATE_DIR>/b1_daily_lock/{market}_{YYYY-MM-DD}.json`

```json
{
  "market": "vn",
  "vn_date": "2025-01-15",
  "status": "IN_PROGRESS",
  "topic_id": "string",
  "pid": 12345,
  "host": "vps-01",
  "created_at_utc": "2025-01-15T02:10:00Z",
  "updated_at_utc": "2025-01-15T02:10:00Z",
  "ttl_seconds": 21600
}
```

Quy tắc: `COMPLETED` thì luôn skip. `IN_PROGRESS` còn TTL thì skip. `IN_PROGRESS` hết TTL thì coi là stale, log WARNING và cho chạy lại. Nếu file hỏng (JSON lỗi) thì log ERROR và skip (fail-closed, không fail-open thành cào lặp).

`STATE_DIR` lấy từ env (ví dụ `AVF_STATE_DIR`), mặc định theo thư mục state hiện có của repo. Đây là điểm then chốt để test hermetic.

### 3.2 Schema cooldown state

Đường dẫn: `<STATE_DIR>/alert_cooldown.json`

```json
{
  "b1_viability::vn": {
    "last_sent_utc": "2025-01-15T02:10:00Z",
    "suppressed_since_last": 3
  }
}
```

Check-and-set phải nằm trong cùng một `flock` để hai tiến trình không cùng gửi.

### 3.3 Checklist kiểm toán B3 subprocess

- Dùng `sys.executable`, không dùng `"python"`/`"python3"` (VPS có thể trỏ sai venv).
- Args dạng list, `shell=False`. Mọi giá trị động không được nội suy vào chuỗi shell.
- `cwd` tuyệt đối, tính từ `Path(__file__).resolve()`, không phụ thuộc thư mục cron gọi.
- `env` kế thừa `os.environ` + `PYTHONPATH` tường minh + `AVF_STATE_DIR`.
- Có `timeout=`, bắt `TimeoutExpired`, kill process group.
- Kiểm tra `returncode != 0` thì raise kèm 2KB cuối stderr. Không nuốt lỗi.
- Không có path kiểu Windows (`\\`, `C:`) hardcode. Đây là nguyên nhân phổ biến của lệch local/VPS.
- Nếu B3 trả dữ liệu cho bước sau qua stdout/file, đối chiếu schema với `.codemap/codemap.json`.

**Task 5: Hardening B3 subprocess** theo checklist 3.3.

**Task 6: Test hermetic** (mục 5).

**Task 7: Kiểm tra đồng bộ VPS (chỉ đọc)**
So sánh `git rev-parse HEAD` local vs VPS, `pip freeze` diff, phiên bản Python, timezone hệ thống (`timedatectl`), crontab entry. Báo cáo chênh lệch.

**Task 8: Deploy**
Dừng lại, trình bày diff và lệnh deploy, chờ người dùng xác nhận rồi mới chạy.

## 5. Verification Protocol & Acceptance Criteria

Hermetic nghĩa là: `tmp_path` làm `AVF_STATE_DIR`, registry thật dựng từ dữ liệu ghi ra file thật, không gọi mạng ra ngoài. Để giữ Zero-Mock cho Telegram, test dựng `http.server` thật trên `127.0.0.1` và trỏ base URL của Telegram qua env vào đó. Request HTTP là thật, chỉ đích đến là local. Nếu code hiện tại hardcode `api.telegram.org`, Task 4 cần thêm env override (giữ default như cũ).

Test bắt buộc (`tests/test_b1_daily_lock.py`, `tests/test_alert_cooldown.py`, `tests/test_b3_invocation.py`):

1. Registry có tập market `vn` ngày VN hôm nay: B1 exit 0, log SKIP, server crawl local nhận 0 request.
2. `now = 2025-01-15T17:30Z` (tức 00:30 ngày 16 VN), registry có tập ngày 15: B1 không skip. Đây là test chống lỗi UTC.
3. Lock `IN_PROGRESS` còn TTL: skip. Hết TTL: chạy, có WARNING.
4. Lock JSON hỏng: skip, có ERROR.
5. Hai tiến trình `multiprocessing` cùng `acquire_in_progress`: đúng 1 thành công.
6. Alert: gửi lúc t0 → server nhận 1. t0+1h → 0, suppressed=1. t0+4h01m → nhận 1, nội dung chứa `+1 suppressed`.
7. Server alert trả 500: không ghi `last_sent_utc`.
8. B3: chạy subprocess thật với `cwd` khác repo root vẫn thành công. Script con exit 3 thì caller raise kèm stderr tail.

Lệnh:

```bash
python -m py_compile utils/daily_market_lock.py utils/alert_cooldown.py <b1_file> <b3_file>
python -m pytest tests/test_b1_daily_lock.py tests/test_alert_cooldown.py tests/test_b3_invocation.py -v
AVF_STATE_DIR=$(mktemp -d) python <b1_entrypoint> --market vn ; echo "exit=$?"
```

Acceptance: tất cả exit 0. Live run lần 2 liên tiếp trong cùng ngày VN in `B1 SKIP` và không có log crawl nào. Trên VPS sau deploy (khi đã được duyệt): theo dõi 24h, mỗi market có tối đa 1 lần crawl đầy đủ khi đã sản xuất tập và tối đa 6 alert/ngày.
